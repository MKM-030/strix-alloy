## Lookup decision

The [complement audit](halogen-strata-lookup-complement-20261006.md) resolves
native `HALOGEN_PLD_LOOKBACK` to default zero (full initial indexing). A Strata
self-history match of at least three actual tokens implies an existing native
hash key when the same history is fully indexed. Its four positions and longer
backward match can change selection at a hit, but cannot fill a genuine key miss.
This supersedes the earlier assessment's unchanged same-history no-hit priority.

Root implemented the small [reproducible owned-ID replay](../../scripts/benchmarks/halogen_strata_lookup_replay.py)
with the Strata MIT notice retained. It uses the hash-verified 8,192-ID shifted
seed and only previously committed outputs at each of 15 retained round bases.
Future output labels are evaluated after lookup and never indexed. The full
available seed is used; the missing original first input ID is never guessed.

One first replay confirmed the independent audit's normal lookup result and
screened the distinct hybrid lookup after two **observed native MTP IDs**. A
source reviewer identified a reporting omission: the first-ID-trigram diagnostic
needed a separate check for the hybrid query. Root corrected that diagnostic
and performed one corrected replay; both raw receipts remain preserved.

There are 14 complete third-token labels and one incomplete final label. Zero
candidates supplies no acceptance denominator. These are policy reconstructions
from one request family, not native map/hit observations, independent neural
predictions, hardware execution or serving rates. Actual native eligibility,
opening, allowance, readiness, capture overhead and all new tok/s values remain
null. No extra engine cohort is justified by this sample. Hit-rich independent
raw-ID data could justify a different selection screen; using future outputs as
a retrieval corpus would leak labels.

Pending-MTP lookup chaining is structurally different from ordinary self lookup:
it asks about the suffix **after** unverified MTP IDs. It would require a separate
verified state/insertion boundary before native target verification. The current
trace provides no useful extension, so no controller modification was attempted.

## Accelerator and ensemble implications

CPU is the appropriate place for bounded token indexing, lookup and host
publication. These new connections add CPU work and have no demonstrated
throughput gain. Neither GPU nor NPU executes in this development. GPU stays on
the native target/MTP kernels. A future GPU or NPU proposer must supply useful
timely complementary IDs and beat stock total elapsed time per committed token,
including contention, transfer, verification, replay and fallbacks.

Several trained diverse drafters can increase candidate coverage, but do not
guarantee 100% native acceptance or higher Decode. The current native consumer
still accepts one linear chain of at most three IDs, without a branch/tree
verifier. Arbitrary weight/agent partitions are not trained complete predictors.
Speculation supplies no direct acceleration of ordinary target Prefill. The
[multi-draft assessment](halogen-multi-draft-feasibility-20261006.md) and pinned
[Strata assessment](strata0140-halogen-source-assessment-20261006.md) remain source
references, with the lookup priority narrowed by the follow-up above.

A subordinate's additional native-controller hook audit ended with an automatic
"possible cybersecurity risk" flag. It was not retried or represented as
completed. The safe owned-ID algorithm screen above was completed instead;
native controller integration remains unqualified.

The full acceleration goal remains active and unachieved. Existing defeated
GPU/NPU/CPU screens and completed engine cohorts must not be repeated unchanged.
