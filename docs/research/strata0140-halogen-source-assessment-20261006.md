# Strata v0.1.40: source assessment for the Halogen HGN work

Date: 2026-10-06. Scope: source inspection only. No Strata build, script execution, engine launch, model download, hardware experiment, or Halogen lifecycle action was performed by this reviewer.

## Practical conclusion

Strata supplies real, inspectable gfx1151 HIP implementations and useful speculative-decoding code. It does not supply a compatible Halogen HGN kernel patch or an already-qualified Halogen neural proposer. The smallest concrete reuse candidate is its token-history `SuffixDrafter` plus `DraftSource` selection, running outside the native hook and publishing through the existing authenticated packet/handoff boundary. That candidate needs only owned token IDs. Its incremental yield after Halogen's own PLD miss remains unknown because both perform lookup.

**Follow-up decision:** the [completed lookup screen](halogen-strata-followup-status-20261006.md) supersedes that initial candidate priority. Same-history lookup and lookup after two observed native MTP drafts each produced zero candidates in the 15 retained cases. The unchanged mechanism is retired for this request family; a useful independent corpus or another mechanism would need new evidence. The GPU kernel and neural-producer source assessments below remain relevant, without a qualified Halogen speed gain.

The neural `MtpDrafter` is a larger follow-on candidate. It requires model weights, embedding/head formats, draft KV/state and target residual rows. The current Halogen value boundary supplies token IDs and authority, not those residuals. Source availability can avoid reverse-engineering an independent producer's implementation; it does not create a residual export, compatible HGN pack, or right to use a model or binary.

Strata may also be a future *different-engine* gfx1151 benchmark arm. Such a result would describe Strata with its own pack, quantization, runtime and settings. It would not establish Halogen optimization, matched-engine parity, or a Halogen serving-rate gain.

## Multi-client batches, speculative rows, and heads

`--batch` represents independent conversations with per-slot session/KV state. `--batch-mtp` is opt-in, requires serving, at least two slots, MTP/speculation, and one GPU without a layer split/helper. It creates a drafter per slot and limits each to one proposal. In `batch_step`, each active MTP slot occupies two verifier rows: the current token and its proposed next token. The eight-row window admits at most four such slots per wave and rotates additional slots. The target's comparison decides whether a slot commits one or two rows. This is concurrent-client batching, not multiple alternative heads voting on one conversation. [Conditions and slot initialization](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/src/program/generate.cpp#L3474), [batch-step implementation](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/src/program/generate.cpp#L7492).

A single-client MTP chain generates successive proposed positions. Its multi-row catch-up/front, multi-token GR, batched KV append and multi-row argmax kernels process token rows. They do not establish multiple independent neural heads competing for the same frontier. Likewise `DraftSource` selects a candidate from sources using the best matching suffix; selection is not evidence that multiple neural proposers run concurrently. A future independent Halogen producer could compete for memory, GPU execution and bandwidth with the target even if it uses a separate stream. Total authoritative committed-token throughput, rejection cost and resource contention would require measurement.

## Prioritized adaptation candidate

[`suffix_drafter.cpp`](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/src/spec/suffix_drafter.cpp) indexes owned history by trigram hash with four recent positions. `propose` compares real tokens backward, picks the longest match/newest tie, and returns following history IDs. `propose_after` temporarily adds pending IDs without indexing them and restores history length. [`draft_source.cpp`](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/src/spec/draft_source.cpp) selects the best qualifying source match.

An adaptation must bound history and capacities, handle allocations/overflow and 32-bit positions, and have one explicit thread owner. Its table/vector allocation and virtual source calls belong outside the hook. Populate committed history from the exact owned initial seed and sealed authoritative emitted IDs; pending or rejected drafts never become committed history. Cap each publication to the current actual B and the existing maximum three custom IDs. Preserve packet identity, epoch/frontier authentication, native opening comparison and target verification. Acceptance, no-hit yield and end-to-end speed remain unmeasured.

The larger neural route is visible in [`mtp.hpp`, `bind`](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/include/strata/core/mtp.hpp#L75): `WeightTable`, `NativeHead`, and device `window_R` residual rows are inputs. Prompt/draft KV and model state also belong to the producer. Q4 conversion in `make_q4_dense` converts Strata Q8_0 tensors to GGML Q4_0; it is not HGN pack support. Its asynchronous `chain_launch`/`chain_outputs_ready`/`chain_poll` mechanism publishes tokens only after per-step event readiness, a useful design reference if owned producer state is later supplied. None of this authorizes dereferencing native addresses from the register observer.

## Benchmark method and licensing

[`tools/hip/bench_prefill.py`](https://github.com/Niko1221/Strata/blob/1735d6471df29b42c26170efaac1f1446a58640f/tools/hip/bench_prefill.py) probes fresh/follow-up requests against an otherwise idle existing Strata server with fixed greedy request settings. It requires exactly one timing line and rejects a fresh arm that reused prompt tokens. It does not manage the service, prove the release table, or compare HGN against GGML. A later comparison would need explicit model/tokenizer/template, context, quantization, KV and residency settings plus quality/output checks. This reviewer executed no benchmark.
