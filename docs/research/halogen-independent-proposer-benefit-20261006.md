Native eligibility counters belong to a later root-owned integration measurement, not another disconnected stock run now.

For a comparable round population, let `k` be stock committed tokens/round, `t` stock round time, `h` hit coverage, `q` timely reply fraction, `g` native opening pass fraction among ready hit replies, and `d` the conditional improvement in committed tokens over stock. Let `c` be added unhidden proposal/transport/rebuild/startup cost per round, including work on unusable replies. If contention stretches retained target work by fraction `p`, the simplified break-even condition is:

`h*q*g*d > k*(p + c/t)`

Changed verification width, fallback, replay and stop behavior must also be included in `c`; this relation is a planning bound, not a measured complete-engine model. In particular, `d` compares to stock acceptance, not zero drafts. A correct first token is not itself an extra committed token over stock.

The retained replay sample committed 37 tokens in 15 rounds: `k=2.4667`, with 22 matched drafts over 30 depth2 proposals. The abstract three-ID maximum commits four tokens, so a generous conditional improvement ceiling is `d<=1.5333`; actual hit-subset stock performance and final allowance can lower it. The 12/15 head ceiling is specific to these prefixes and is not a population gate-rate estimate.

## When append-only state is valid

The default-off [reference coordinator](../../scripts/benchmarks/halogen_pld_transaction.py), SHA-256 `e19723b339ecf4ae60c3add6737d1ed50cfe0cfdef2d133ecd742c88449ec7b6`, predicts its first ID from copied committed-prefix logits. Count1 consumes **zero** speculative inputs. With no window shift, cancellation or unsupported ID, an engine can then forward only authoritative accepted/correction/bonus IDs and remain coherent without checkpoint rollback. Root added this opt-in `append_when_authoritative` path during the audit; its default remains clear/rebuild.

For a length `n` proposal, the engine consumes `n-1` speculative inputs. Append-only synchronization is safe only if every consumed input is accepted: `a>=n-1`. Thus length3 needs at least two accepted drafts; length2 needs at least one. Remaining authoritative outputs can then be forwarded in order. A rejected consumed input, stale/unused speculative reply or rebase still requires full rebuild until attention rollback is qualified. Owned logits/history/positions and request/round epochs remain necessary.

A strict rolling 512-token window initialized at 512 shifts on every authoritative advancement, so count1 alone does **not** remove rebuilds. For the finite append pilot, select the last **256** seed IDs and permit growth within **512**; all 37 retained authoritative updates then end at 293 IDs without a rebase. Retire/rebuild at the bound. This changes the context policy from last512 to a shorter growing window; measure its accuracy separately rather than claiming equivalence. The workload records this pilot separately from the fifteen last512 frozen cases.

Focused source-only review found no concrete correctness bug in the new path: pending logits describe exactly `n-1` consumed drafts, `accepted>=consumed` proves them authoritative, equal window origin rules out a rebase, and `outputs[consumed:]` forwards precisely the remaining authoritative tail. The coordinator retires the old state before mutation, so append failure leaves no live feed. Root's fixture changes cover rejected consumed drafts, window shift, append failure and fresh-fixture logits parity. This audit did not run those tests. The real FLM bridge must still complete raw forwards, deep-copy logits and honor capacity/lifetime; the optional path introduces no additional bridge incompatibility identified here.

Count1 cannot improve a proposal suffix. The unchanged opening gate fixes every admitted first ID to the native head, and stock depth2 already gains from many second drafts here. Replacing blocks with count1 can reduce useful batching; the retained [greedy depth1 results](../benchmarks/halogen0162-greedy-depth1-results-20261004/README.md) already show that higher accepted fraction can accompany lower speed. Treat count1 as a state/latency option, not the default claimed acceleration.
