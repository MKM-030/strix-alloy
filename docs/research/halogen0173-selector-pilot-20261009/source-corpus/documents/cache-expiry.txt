A Rust service keeps a small cache of parsed configuration files. It uses a monotonic clock so that wall-clock adjustments do not alter expiry. Each entry records when it was inserted and a value that can be cloned. The service is single-threaded; callers hold a mutable reference to the cache. The policy is a fixed time-to-live from insertion. Reading an entry must not extend that lifetime. A zero lifetime means that no entry can be returned from the cache.

```rust
use std::collections::HashMap;
use std::time::{Duration, Instant};

struct Entry<V> {
    inserted: Instant,
    value: V,
}

struct Cache<V> {
    entries: HashMap<String, Entry<V>>,
    ttl: Duration,
}

impl<V: Clone> Cache<V> {
    fn get(&mut self, key: &str, now: Instant) -> Option<V> {
        let entry = self.entries.get_mut(key)?;
        if now.duration_since(entry.inserted) > self.ttl {
            self.entries.remove(key);
            return None;
        }
        entry.inserted = now;
        Some(entry.value.clone())
    }
}
```

The implementation has accumulated several problems. A read resets inserted, so a frequently accessed entry can survive forever despite the fixed-lifetime policy. The comparison is strictly greater than ttl, whereas an entry should expire exactly at its deadline. A test can pass a now earlier than inserted, and the team wants that case to return None without relying on panic behavior or a clock saturation detail. The mutable borrow can also make removing the entry awkward, depending on how the function is rewritten. The service should remain easy to inspect.

The tests use a base Instant and offsets created with Duration. One test inserts at base and reads at base plus ten seconds with a ten-second lifetime. Another inserts at base plus five seconds, then reads at base. Both must return None. A third inserts at base, reads at four seconds, and reads again at nine seconds; both reads should return the original value, with no change to the insertion time. A fourth reads again at eleven seconds and should remove the expired entry. Removing expired entries is part of the contract, because otherwise keys can accumulate indefinitely.

The cache stores at most a few hundred entries, so cloning a value on a hit is acceptable. The task does not require background eviction, a global cleanup pass, an LRU policy, or concurrency primitives. Do not introduce a second clock or change the caller's time representation. There is also an insert method, omitted here, which replaces an existing entry and records the supplied insertion time. That behavior should remain as stated.
