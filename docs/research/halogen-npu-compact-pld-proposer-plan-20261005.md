# Compact NPU token proposer for the private PLD seam — 5 October 2026

**Prioritize Qwen3.5-0.8B as one real, token-only autoregressive proposer, using the prepared FastFlowLM NPU2 package.** This is a bounded candidate plan, not a working feed or a speed result. The finite [offline proposal adapter](halogen-npu-pld-proposal-wire-20261005.md), [exhaustive shared token-map comparison](halogen-npu-pld-tokenizer-compatibility-20261005.md), [source/installed-DLL checkpoint audit](halogen-npu-pld-raw-id-checkpoint-20261005.md) and default-off [reference transaction coordinator](../../scripts/benchmarks/halogen_pld_transaction.py) are complete. A real engine bridge, native consumption, the necessary weights and runtime accepted-prefix transactions remain unqualified. Establish a concrete prediction path and plausible complete-engine benefit before model acquisition or hardware work.

## Private seam and bounded state contract

The [static insertion audit](halogen-npu-native-pld-injection-scope-20261005.md) identifies RVA **`0x172e95f`**, after native copying of context IDs and before constraint handling and native first-head equality. It is **PLD-hit-only**: native lookup remains, and no-hit rounds cannot receive this feed without a separately qualified insertion. Keep the native opening gate, target verifier, accepted-prefix handling, replay, grammar and stop/EOS behavior. An independent first-token mismatch takes the stock MTP/scalar fallback; do not manufacture that token from future target predictions. Start without a constraint object and cap the reply at `min(stock_n, 3, native_allowance)`. All invalid, stale, late or unavailable replies retain the untouched stock block/count.

Own the proposer state separately from Halogen. Bind every reply to an explicit request-initialization nonce, committed token position, committed-prefix fingerprint, context-window origin and one-shot round identity. Native object pointers and counts do not establish freshness. Reset, replacement, cancellation and failed initialization must retire the nonce and outstanding replies. The native audit supplies birth/destructor anchors but does not yet prove all reset/cancel synchronization or a live shim.

Initialize with **256 committed tokens**, allow finite growth to **512**, then rebuild the retained window when its origin shifts. These are logical history limits, not qualified FLM allocation settings: the matching DLL constructor clamps device capacity to at least 4,096. Prefill once per window or rebuild, then predict at most three IDs from available committed context. After native verification, synchronize to the actual accepted prefix plus target correction/bonus. Discard every rejected draft suffix. A shifted rolling window changes recurrent/attention state and requires a correctly bounded rebuild unless the runtime proves an equivalent operation; dropping IDs from host history is insufficient. Starting immediately at the 512-token cap would require a shifted-window rebuild after every advancement and defeat the append optimization.

The checkpoint audit pins the installed XRT `qwen3_5vl_npu.dll` to SHA-256 **`d77388dcd21fcd7422005d0f780a044142d525e3afaafef3bcb9e980b8c18501`**, byte-identical to the FLM 1.0.7 source bundle's XRT DLL. Its observed checkpoint/restore copies the complete persistent linear-layer buffers, covering convolution history and recurrent S, saves both position counters, and rebuilds decode sequences/run state and RoPE position. It stores one latest checkpoint. The audit parsed the matching Windows vtable, but exported calls still require a qualified Windows C++ caller, matching headers/import library, XRT/MSVC/STL/bf16 layouts and mapped-buffer lifetime. This is a concrete candidate mechanism, not a ready raw-ID service; HRX and other DLL versions do not inherit the finding.

Checkpoint omits **logits, caller token history, last token and sampler state**. Raw `forward(int)` returns a shallow view of a reusable output buffer, so the adapter must deep-copy committed-prefix next-token logits and own the authoritative history/position. Stateless greedy selection must use only the shared defined IDs. `clear_context()` clears persistent state and counters but leaves the DLL's snapshot flag set: a clear, rebase, request replacement, cancellation or capacity/model change must invalidate the adapter's snapshot epoch, and only a fresh checkpoint can authorize later restore. The high-level FLM generation path adds think/newline tokens, so raw committed IDs must bypass it.

Exact attention rollback remains blocked by a specific observation. Restore zeroes K/V starting at the **current speculative length**, leaving rejected rows between the saved prefix and that length. Replay writes at the correct saved-prefix append slot, but cache DMA rounds its read span to sixteen rows. The host reprograms the restored logical length; the executed attention firmware's exclusion of stale padded rows was not proven. Until restored/replayed logits match a fresh authoritative replay, **clear and rebuild from the authoritative committed window is the correctness fallback after a speculative round**. This includes rejection, and its cost belongs in every benefit estimate. HTTP full-prompt replay alone does not supply the transaction contract.

After that qualification, a checkpoint optimization can save the fully consumed committed prefix and owned logits, predict up to three independent IDs, restore, then replay the target's actual accepted IDs plus correction/bonus and take a fresh checkpoint. Reserve engine capacity for up to three speculative inputs and up to four authoritative output IDs; do not evict or resize a checkpointed prefix mid-round. No target correction or future verification row may become proposer input before it is authoritative. Window shifts still require a separate qualified rebase or rebuild.

The selected language payload is about 535 MiB on disk; the manifest's declared footprint is 1.3, not a measured residency result. At 2,048 tokens, configuration-derived bf16 K/V storage for the six full-attention layers alone is about 24 MiB, before recurrent state, convolution history, checkpoint copies, logits, activations and runtime allocation. This makes a bounded candidate plausible enough to prioritize, but neither proves the allocator honors the requested bound nor permits omitting rebuild/prefill cost. Optional vision weights are outside this token-only design; whether the prepared loader can avoid them still needs qualification.

## CPU and GPU realizations

The same token-proposer architecture can use a CPU or GPU engine: consume the supported committed IDs, predict a bounded block independently, let the native target verify, and synchronize the private proposer to authoritative output. Such an engine must either restore all mutable recurrent/convolution and attention state with positions, or deterministically clear/rebuild the committed window. It also needs the same owned logits/history, snapshot epochs and unsupported-ID fallback. The audited FLM DLL is **NPU/XRT only**; it supplies no CPU or GPU backend. Each alternative needs its own model artifact, raw-ID caller and state qualification. The separate GPU H proxy is not a token proposer.

CPU and GPU execution offer no established gain here. Measure their proposal and replay/rebuild time, startup, model/cache/snapshot residency, transfers, host scheduling and contention with target execution. GPU compute/memory contention can offset overlap; CPU work can contend with the target's host scheduling. The native hit-only coverage and opening-head gate remain unchanged on either backend, and exact target acceptance remains an empirical property of independently predicted IDs.

## Acceptance and benefit gates

**First source milestone implemented:** [the default-off raw-ID transaction coordinator](../../scripts/benchmarks/halogen_pld_transaction.py) connects the completed packet binding/encoder to an injected `clear_context`/`prefill`/`forward` engine. `reset(binding, committed_ids)` initializes a supported window with a fresh caller-supplied nonce; `propose(binding, max_drafts=3)` returns independent greedy IDs and an authenticated packet; `apply(outcome, next_binding, outcome_is_authoritative=...)` checks the accepted draft prefix and authoritative advancement, then clear/rebuilds the resulting window; `invalidate()` retires cancellation/replacement. The independent authority callback must validate the target outcome and next prefix fingerprint; constructing an outcome object alone supplies no authority. Native gating, constraints, hit coverage, stop behavior and live synchronization stay outside this module. There is no checkpoint fast path.

The coordinator validates all retained input/current/proposal IDs against 0–248069, owns immutable history/position and copied supported-row logits, permits one pending round, and declines unsupported authoritative correction/bonus IDs. Every enabled reset attempt retires the preceding state before validation, including failed initialization and nonce reuse. Budgets are finite: at most 64 request nonces per coordinator and 64 consumed rounds per request. The engine needs room for **512 committed IDs plus two speculative forward inputs** to predict three IDs; an authoritative outcome contains up to four IDs, then the coordinator rebases to the last 512 before clear/prefill. Membership/fingerprint truth before the retained window and initial native position semantics remain caller responsibilities.

**Default-off append optimization:** `append_when_authoritative=True` retains the private engine only when the accepted prefix covers all consumed speculative inputs and the window origin is unchanged. Predicting `n` IDs consumes only the first `n−1`; the final proposal is a prediction from owned logits. For `n=1`, no speculative forward occurred, so a zero-acceptance correction can append safely. For `n=3`, at least the first two proposals must be accepted; then only remaining authoritative output is forwarded. Otherwise clear/rebuild remains mandatory. An append exception retires the feed. This optimization uses no checkpoint or attention rollback and applies equally to CPU/GPU engines with the same raw-ID contract. Fixture parity against fresh authoritative replay is qualified; real FLM prediction parity and complete-engine latency remain unqualified.

Three [CPU fixture transaction tests](../../scripts/benchmarks/test_halogen_pld_transaction.py) cover default rebuild plus optional append parity against fresh authoritative replay, insufficient accepted-prefix fallback, shifted-window rebuild, failed append retirement, reset/stale outcome/failed initialization, and disabled/unsupported-ID retirement. Root ran these together with the three proposal-wire tests: **six focused tests passed**. They exercise coordinator behavior and packet decoding with a prefix-dependent reusable-logit fixture, not FLM predictions or native acceptance. Python per-logit conversion/copy and argmax are reference behavior; a production NPU/GPU engine bridge needs efficient native buffer/argmax handling and separate cost measurements.

The remaining exact correctness blockers are the instantiated Windows caller ABI and mapped-buffer lifetime; real engine capacity/window-rebase behavior; and native live hit consumption with complete reset/cancel/lifetime synchronization and authoritative binding truth. Any later checkpoint fast path also requires fresh runtime snapshot epochs and attention masking/parity across padded row boundaries. Prepared weights are absent, and token-only loader behavior is unqualified. After a real prediction path exists, record native-hit coverage, first-head gate pass rate, exact accepted-prefix lengths 0–3, stale/late replies, fallback rate and all initialization/rebuild costs. A hit-only feed can improve an existing PLD suffix, but cannot claim the coverage of a no-hit drafter. Quantization, context truncation, model size and target/drafter distribution differences may make exact acceptance too low even when text looks reasonable.

Use held-out target prefixes split by complete documents/requests, with no saved answers, future verification rows or prompt-copy leakage as proposer inputs. Compare to the unchanged native PLD/MTP policy on the same requests. Any later distillation should teach the target's next IDs from available prefixes and be justified by held-out accepted-prefix improvement; text quality or perplexity alone is insufficient. Pin the training/evaluation/tokenizer/package revisions. A trained quantized artifact would need a new export and qualification, not inherit this prepared checkpoint's receipt.

The required result is lower elapsed time per **actually committed token** on matched work. Include proposal generation, transport, packet checks, retained native lookup/opening-head work, target verification/commit/replay, rejection fallback, window rebuilds and shared-memory/scheduling contention. Count missed readiness and startup over actual requests. The existing small-model throughput is not a break-even estimate, and another disconnected FLM benchmark would not qualify this plan.
