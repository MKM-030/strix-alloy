## Windows and the actual runtime path

AMD identifies FP11 as the CPU socket. MLIR-AIE instead selects the NPU architecture: its device documentation includes Strix Halo under `npu2`, and its XRT runtime maps both `Strix Halo` and `npu5` to that target. FP11 is therefore not a missing compiler architecture. This establishes documented architecture eligibility, not a new installed-host qualification. [AMD product specification](https://www.amd.com/en/support/downloads/drivers.html/processors/ryzen/ryzen-ai-max-series/amd-ryzen-ai-max-plus-395.html), [pinned device documentation](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/docs/Devices.md#L43), [runtime mapping](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/python/utils/hostruntime/xrtruntime/hostruntime.py#L95).

The native guide supports Windows 11, MSVC, Windows XRT SDK 2.21.75 and CPython 3.13 `pyxrt`. Its repository minimum is driver 32.0.20101.3760 / XRT 2.21.0. Retained October 5 evidence used MLIR-AIE 1.3.4 and driver 32.0.20102.3930; the isolated SDK 2.21.75 was also already used for the FLM bridge. Those are historical receipts, not a fresh driver query or proof that 1.4.4 is installed. [Pinned native guide](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/docs/buildHostWinNative.md#L84).

The loader registers an xclbin, creates an XRT hardware context and kernel, then submits and waits. Dynamic `DispatchTime` calls construct a fresh instruction transport, copy instructions and synchronize that BO before submission. `XrtTransport` allocates the underlying BO. Caching a compiled design therefore does not establish zero allocation or lower runtime latency. The wrapper submits an `insts_bytes` field; the retained native fixture describes word-count ABI semantics, so emitted artifact/runtime compatibility must be checked before migration. [Pinned runtime](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/python/utils/hostruntime/xrtruntime/hostruntime.py#L336), [transport allocation](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/python/utils/hostruntime/xrtruntime/tensor.py#L29).

The WSL guide compiles device code in WSL and uses a Windows host application. It supplies no Windows-XRT-to-WSL-HIP import/fence contract. The HSA discovery source explicitly limits the AIE agent to Linux and gates its library layout accordingly; the new HSACO packer does not change that Windows boundary. [WSL guide](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/docs/buildHostWin.md#L11), [Linux-only HSA source](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/python/utils/hostruntime/hsaruntime/discovery.py#L24).

## What the release changes

Dispatch-time scalars and dynamic DMA can vary a compiled operation's transfer bounds. The official copy test retains one cached kernel/artifact pair while generating differently sized instruction streams; it tests behavior, not proposal latency. Flash Attention prefill, q4nx dequantization, BF16 GEMM fixes and compiler/kernel caching are useful building blocks. They supply neither trained conditional token weights nor an automatic modification to the existing FLM DLL. [Pinned dispatch test](https://github.com/Xilinx/mlir-aie/blob/e5c705c7b04bb8470db7364287843ba96e487a6e/test/python/npu/test_dispatch_time_scalar.py#L92), [release details](https://github.com/Xilinx/mlir-aie/releases/tag/v1.4.4).

## Smaller-model conclusion

An official `FastFlowLM/Qwen3-0.6B-NPU2` package exists. Its configuration has a 151,936-entry vocabulary, while the already qualified Qwen3.5-0.8B bridge uses shared defined target IDs 0–248069. The smaller package is not qualified to consume arbitrary committed target IDs directly. Retokenization, target-ID projection, state advancement and rollback would require a different adapter and fresh quality/cost evidence. Neither a compatible smaller package nor its local timing was established here. [FLM 0.6B configuration](https://huggingface.co/FastFlowLM/Qwen3-0.6B-NPU2/raw/main/config.json), [retained proposer screen](halogen-npu-independent-proposer-screen-20261006.md).

The retained native Windows complete timings are **77.183 µs GEMV / 82.263 µs control**, including input copy, synchronization, launch/wait and output readback. The FLM three-ID proposal costs **45.218 ms**, consumes two forwards, and needs **22.461 ms** per authoritative append or **418.29 ms** for the tested 512-ID rebuild. These are different tasks: subtraction is not an isolated compute measurement. They do show that 45 ms is not an unavoidable Windows small-dispatch floor. [Native evidence](halogen-npu-native-route-20261005.json), [FLM evidence](halogen-npu-independent-proposer-screen-20261006.json).

A plausible future candidate is a trained same-tokenizer predictor with resident state and few fused kernels. It still needs complete-prefix state qualification, a causal router, native packet/outcome integration and matched complete-cost measurements. The earlier opening-conditioned offline audit found 18 leading NPU matches versus 19 stock accepted drafts on the same ten rounds; it supplied no native acceptance or live gain. Existing no-hit relay scaffolding alone does not close those requirements. No defeated screen was repeated.
