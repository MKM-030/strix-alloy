# First live duration-adapter cohort: rejected Decode pairing

The first live 0.17.3 duration adapter paired Prefill successfully, but every Decode end failed its strict pairing check. This cohort is rejected as a complete RAW-qualified serving benchmark. Its unchanged API observations are retained for diagnosis: measured means 1843.65 Prefill tok/s and 44.58 Decode tok/s; combined MTP+PLD acceptance 180/399 = 45.11%. These means establish no new speed gain.

Halogen constructs a temporary request on the stack at the Decode start and moves it into a heap-backed request vector before reporting Decode completion. The adapter incorrectly required object-pointer identity across this move. Native request IDs remained 3, 4, 5 and 6; all four ends reported missing-pair status 3, and two later starts reported duplicate status 5. The adapter returned the original native Decode clock values on these failures. The strict verifier rejected the journal; no tolerance or gate was relaxed.

The frozen cohort contained one excluded warmup and three measured requests, each with 16384 actual natural-story input tokens and 128 ordinary output tokens. Temperature 0 / seed 1, Thinking Off, Cache Off, MTP2 / PLD3,3, context capacity 262144, chunk and arena 8192. All four output hashes and accepted/drafted counters matched the prior frozen request. Whole-request RAW/QPC observations passed 0.1% and physical/commit reserves stayed above 18 GiB. These checks do not repair missing phase pairs.

Root retained the original response, journal and explicit rejection receipt. The first extraction copied both journals before failing to convert a Windows capture destination into a Linux path; the existing extraction was completed by the correct converter, without replaying a request or overwriting its journals. The authentic GPU component capture occurred in the excluded warmup; its independent result is [documented separately](../research/halogen0173-scratchfree-moe-20261009.md).

Before this cohort, the normal server stop completed owned resource cleanup but failed the original historical free-memory recovery target. A separate deliberate restart verified exact dead controller/backend identities, the exact owned terminal container, quiesced helpers and five current 35/131 GiB admission frames. Only the matching orphan lock was released. The original failed outcome/recovery files remain unchanged; the restart retained normal admission and the 18 GiB runtime guard. This is new startup admission, not a claim that historical recovery passed.
