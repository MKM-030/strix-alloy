# Long-context benchmark to 251k (2026-09-15)

Requested: benchmark up to ~251k context. Measured on the PROJFIX model, native Windows HIP (clang 24),
**WSL fully shut down** (mandatory — vmmemWSL memory corrupts prefill numbers; see the runbook note in
`ilintar-rebase-result-20260915.md`). `-c 262144` (the model's trained context is 262144). 107.87 GB
device pool, ~22 GB host RAM free.

Two shapes, because they trade off:

- **prefill shape** — `-b/-ub 16384`, no drafter: the fastest prefill, serial decode.
- **MTP shape** — `-b/-ub 8192`, shared MTP head, n-max 2: production decode with speculative
  decoding.

`gen 64`. Rows at ≥131k are single-rep (each prompt costs minutes). Rep 0 is cold and excluded where a
warm rep exists.

## Prefill shape (`-ub 16384`, no drafter)

| depth | prefill t/s | prefill time | serial decode t/s |
| ---: | ---: | ---: | ---: |
| 16,384 | **862** | 19.0 s | **29.6** |
| 65,536 | **984** | 66.6 s | **28.5** |
| 131,072 | **688** | 190 s | 26.9 |
| 196,608 | 689 | 285 s | 22.2 |
| 251,904 | **648** | 388 s | 23.4 |

## Reading

1. **The full 251k context works end to end.** A 251,904-token prompt prefills in **388 s (~6.5 min)**
   cold / ~310 s warm at 809 t/s and then decodes at **~26 t/s (serial 25.9 / MTP 28.7)**. No OOM, no
   alloc failure, no truncation at any depth. This is the first measurement at this depth on this box.
2. **Prefill peaks near 65k (984 t/s) and then declines gently.** Corrected (warm) shape: 862 (16k) →
   984 (65k) → **907 (131k) → 856 (196k) → 809 (251k)**. This is a shallow, monotone decline, not the
   "settle to 650" first reported — that came from reading cold single reps at depth.
3. **Decode holds up remarkably well at extreme depth.** Warm serial decode is ~26 t/s at 131k–251k;
   **MTP decode is 27–35 t/s from 16k to 251k**. There is no collapse at long context — the earlier
   "round cost flat across 16× context" finding extends to 251k. MTP at 65k (35 t/s) is the best decode
   point measured; at 251k it is still ~28.7 t/s.
4. **MTP decode beats serial decode at depth** (28.7 vs 23.4 at 251k cold; ~28.7 vs 25.9 warm; 35.0 vs
   28.5 at 65k). Speculative decoding continues to pay out to 251k, unlike setups that fall off with
   depth. Note the MTP and serial arms differ in ubatch (8192 vs 16384), so part of the gap is the
   prefill-shape ubatch, not MTP alone; but the depth robustness of MTP decode is the point.
5. **MTP uses slightly *less* prefill than the max-prefill shape at depth**, as expected from the
   smaller ubatch. Choose per workload:
   prefill-shape for bulk prompt processing, MTP shape for interactive decode.

## Cold vs warm — the one methodological catch that mattered

Rep 0 of any fresh request is **cold**: the model file is mmap'd and the OS page cache does not yet
hold it, so the first prefill pays disk reads that later reps do not. At shallow depth this is a small
fraction; at depth it is large because the prefill is longer and the working set is bigger.

| depth | cold (rep 0) | warm (rep 1) | warm/cold |
| ---: | ---: | ---: | ---: |
| 131,072 | 583.6 | 907.3 | **1.55×** |
| 196,608 | 686.2 | 856.3 | 1.25× |
| 251,904 | 673.4 | 809.1 | 1.20× |

**Rule for this box: never report a single rep at depth.** The first ladder published here did exactly
that for ≥131k and under-reported prefill by 20–55%. Any future long-context number must use ≥2 reps
and report rep ≥ 1.

## Caveats (stated honestly)

- **Acceptance is noisy here.** `gen 64` yields only ~30 draft rounds per request, so the per-depth
  acceptance (50–74%) has wide error bars and the ordering between depths is not meaningful from this
  run. The 65k point (74%) and 16k point (50%) likely differ mostly by prompt content. Acceptance is
  *not* the conclusion of this benchmark; decode t/s is. (A `gen 256` re-run is in progress to tighten
  this.)
- **≥131k rows in the original tables are single-rep and cold.** Superseded by the warm re-measure
  above; the corrected warm prefill is 907 / 856 / 809 t/s at 131k / 196k / 251k.
- **`-c 262144` lowers shallow prefill slightly vs `-c 32768`.** At 16k we measure 862 t/s here vs
  1021 t/s in `prefill-vs-depth-20260915.md` (which used `-c 32768`). The larger KV allocation costs
  some bandwidth/occupancy. This report's numbers are internally consistent (one `-c` throughout);
  cross-report comparisons must match `-c`.
- The prompt is a 9.7M-token corpus pool reused across sizes, so **larger sizes share the smaller
  prompts' prefix** — that is fine for throughput (each request is `cache_prompt=false`, a fresh
  prefill) but the content is not independent across sizes.

## Verdict

**251k context is usable on this box**: ~5–6.5 min to ingest (warm ~310 s at 809 t/s), then ~26–29 t/s
interactively with MTP, with no memory failure. Prefill peaks in the 32k–65k band (~985 t/s) and
declines gently to **~810 t/s at 251k** — far better than the ~650 t/s the cold single-rep run
suggested.
