# Halogen 0.14.2 + Strix Alloy WSL2 candidate

Status: the patched 0.14.2 candidate completed real WSL2 inference and both frozen benchmark workloads (16 HTTP requests). Engine-reported rates are higher in all four selected cells, but unresolved timing, count-alignment and controller cleanup issues prevent a validated performance-superiority or clean production-qualification claim. The qualified 0.13.8 installation remains unchanged and is the rollback target.

### Limitations and recovery

- Engine/HTTP timing inconsistency persists: one prefix reports 126,180.8 ms
  of engine prefill+decode against 122,422 ms complete HTTP wall. No rescaling
  or strict timing parity is claimed.
- 346 host samples: minimum 17.125 GiB Windows available and 109.756 GiB
  commit headroom; cgroup peak 27.758 GiB. Runtime floors were not crossed.
- The external prelaunch observation passed 47 GiB, but actual admission-start
  was 45.895 GiB. This review-policy discrepancy is retained. The companion
  was corrected afterward to check the reviewed scenario directly at admission.
- Model shutdown succeeded, but automatic baseline-relative memory recovery
  timed out while WSL retained file cache. The original outcome remains failed.
  Separately reviewed, read-only-file-descriptor cache advice on only the HGN
  and overlay files reduced observed WSL working memory from about 8.7 to
  2.6 GiB. No file was deleted and no global cache flush was used. Five fresh
  recovery frames then passed, recorded separately in
  `reports/halogen0142-mixed-manual-recovery-20260928.json`.
- A subsequent repetitive attempt was rejected before any container creation
  for insufficient headroom under the then-reviewed 47 GiB launch scenario;
  it is not a benchmark result. No completed measurement is rerun to hide it.

### Repetitive completion and remaining controller limitation

The independently reviewed revised allocation estimate used the observed mixed
decline of 28.770 GiB with this exact larger-pool profile and the preserved older
repetitive decline of 28.800 GiB. These already include KV/cache. With 4 GiB
uncertainty and the retained 12 GiB runtime floor, the repetitive-only admission
scenario became 45 GiB physical / 116 GiB commit, enforced at both actual
admission points. Mixed remains at 47/116; no runtime floor was lowered.

The actual repetitive admission-start frame was 49,105,739,776 bytes available
(45.733 GiB), with 216,388,714,496 bytes commit headroom. All eight requests
completed and final telemetry was saved. Minimum Windows availability was
16.598 GiB, minimum commit headroom 103.036 GiB, cgroup peak 27.752 GiB and
sampled 8060S adapter commit peak 83.622 GiB. Engine-described allocation was
75.5 GiB (68.0 weights, 3.7 KV, 3.8 working); accounting surfaces overlap.

The owned container stopped (PID0, OOM false, no Docker error) and five recovery
frames passed. However, an independent sampler operation failed near shutdown,
so the controller correctly retained `host guard failed` and a failed overall
outcome. A stop/sampler overlap was investigated; the missing subprocess stderr
does not justify pretending its exact cause is proved. The completed independent
audit (`reports/halogen0142-repetitive-audit-20260928.md`, research parent) found
the overlap plausible, not established. No benchmark was rerun
to erase this error. A later read-only check found no running containers,
52,954,787,840 bytes Windows available and only 1,391,476,736 bytes 8060S adapter
commit, confirming no model-sized allocation remained at that observation.

Further controller hardening and broader correctness testing remain necessary
before promoting this candidate as the default long-running server. The completed
measurements are retained as measurements, not a claim that every qualification
gate passed.

Raw draft counters are not a validated acceptance percentage: the repetitive
selected rows report proposed/accepted counts of 94/95 and 93/94. Their API
semantics remain unresolved; no greater-than-100% acceptance claim or invented

## What is carried forward

Our WSL2 support consists of process-local HIP mapping/registration adapters, a bounded hybrid GPU-copy/host-registration policy, an exact-engine preflight accounting bridge, and guarded launch/cleanup. It is not a modified Windows display driver. Upstream Halogen still does not support WSL2.

The 0.14.2 candidate reuses existing read-only HGN/overlay/tokenizer files. No XL GGUF or other model is downloaded. All modifications stay under the research/integration candidate and generated artifacts; old public profiles and binary seals are not relabelled as 0.14.2.

## Qualification sequence

1. Audit the relocated preflight instruction, stack/register ABI, original 16 GiB floor and unchanged allocation planner. Build candidate-only adapters and run CPU fixtures.
2. Adapt only the upstream host-preflight WSL refusal, requiring the verified DXG runtime and real gfx1151 device evidence. Retain other checkpoint/runtime checks, and disable downloads.
3. Review and run an owned-container trace which exits before model range registration/copies.
4. Review and run one 4096-context/pool correctness session, initially serial; verify new engine/API identity, shutdown and memory recovery.
5. Replay the frozen Reddit mixed/repetitive requests, preserving actual token counts and cache/timing caveats. Only then expand tuning.

Initial private candidate policy: at least 24 GiB Windows available physical memory and 98 GiB system commit headroom before launch; continuous 12 GiB physical/commit stop floors; unchanged 56 GB WSL cap, 44 GiB cgroup with no extra swap, 48 GiB copy cap and 24 GiB registered-host ceiling. These are admission/stop thresholds, not memory reservations or a freeze guarantee. New engine allocation uncertainty must be reviewed before live execution.
