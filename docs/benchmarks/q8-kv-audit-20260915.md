# q8 KV compatibility audit — the fast sparse path HARD-requires f16 (2026-09-15)

Codex Step 5, first half: audit the local sparse-attention path for KV dtype compatibility **before**
running any q8 test. Verdict: **q8_0 KV is not a flag-only change on this fork — the production
sparse path asserts f16.** The correct outcome of the audit is "unsupported: fail explicitly", per
Codex's own taxonomy.

## The two f16 dependencies, and they differ in kind

`src/models/qwen4exp.cpp`, in `build_layer_attn`:

**1. Hard requirement — the fast sparse (`direct_indices`) path:**

```cpp
const bool direct_indices =
    n_stream == 1 && cparams.flash_attn && cparams.offload_kqv &&
    hparams.f_max_alibi_bias == 0.0f && !hparams.attn_soft_cap;   // <-- no dtype check
...
if (direct_indices) {
    GGML_ASSERT(q->ne[0] == 256 && k->type == GGML_TYPE_F16 && v->type == GGML_TYPE_F16);
```

`direct_indices` is **not gated on the cache dtype**, but the block it guards **asserts f16 K and V**.
So with `-ctk q8_0 -ctv q8_0` plus `-fa on` (which we always run), the assert fires and the process
aborts. It does not silently fall back — the `else { build_attn_mha(...) }` branch is unreachable
because the assert is the first statement of the `if`.

**2. Soft requirement — the packed prefill layouts:**

```cpp
if (original_keys->type == GGML_TYPE_F16 && original_keys->ne[0] == 256 && ...) {
    packed_keys = qsa_pack_keys(ctx0, original_keys);   // qsa2/qsa3 consume this
}
```

This one is a **conditional**: with a non-f16 cache it simply does not build packed keys/values, so
`qsa3` is unavailable and the model falls back to the masked `flash_attn_ext` path. Slower, but not a
crash.

## What that means for the test plan

| outcome | our situation |
| --- | --- |
| unsupported → fail explicitly | **this is us, on the production `-fa on` path** |
| supported via slow fallback | only if `direct_indices` were made false (e.g. `-fa off`), which loses far more than it gains |
| supported via efficient sparse kernel | would require a new q8-capable qsa3 kernel |
| supported with dequant/staging | would dequant the whole history every forward — Codex correctly calls this a poor route |

So the honest answer: **q8_0 KV is a kernel project (a q8-capable qsa3 + packed-key path), not a
configuration change.** Its payoff is also bounded: the format-size saving is ~2.8 GiB of a
262,144-slot f16 KV (6.0 → 3.2 GiB from the model's 12 attn layers × 2 kv-heads × 256 dim), which is
a capacity/placement benefit, not an automatic decode speedup — and decode is already not
KV-bandwidth-bound at shallow depth (53% of a 235.7 GB/s ceiling on 4.22 GB of *weights*).

## Empirical confirmation (done)

Launched with `-ctk q8_0 -ctv q8_0 -fa on` and a 1-token generation. The binary confirms the source
reading exactly — **it fails at model load, during the first graph build, not at generation**:

```
0.00.065.355 I srv load_model: loading model '...PROJFIX-00001-of-00009.gguf'
C:/AI/build/strix-llama-win/src/models/qwen4exp.cpp:1411:
    GGML_ASSERT(q->ne[0] == 256 && k->type == GGML_TYPE_F16 && v->type == GGML_TYPE_F16) failed
```

So q8 KV is not a slow-fallback configuration on this fork — it is an immediate hard failure on the
production `-fa on` path. `results/q8kv-*.err`.

## Recommendation

**Do not pursue q8 KV now.** The gate is a missing kernel, not a flag; the benefit is capacity-first
(and we have just shown capacity costs nothing, so the memory saving buys no speed); and building a
dequant/staging path to feed an f16-only kernel would very likely lose to the f16 path it replaces.
Record as `BLOCKED_ON_KERNEL`; revisit only if a q8 qsa3 kernel appears upstream.
