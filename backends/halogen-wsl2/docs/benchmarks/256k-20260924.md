# 256k capacity test — 24 September 2026

**Result: failed before API readiness. No 256k prefill or decode rate was
measured. This configuration is unsafe to retry unchanged on a working PC.**

The test attempted a 262,144-position total KV pool with the current pinned
Halogen 0.13.8 image and the same working bridge, adapters, model and profile
as the original benchmark. Compared with the 32k control, only the context and
total KV-pool limits changed. One slot, arena/chunk 2,048, copy cap 28 GiB,
ROUTE_GEMM=0, cache=0, SDMA=1 and selective copied-weight reclaim remained set.
Windows VGM stayed 32 GiB; the WSL ceiling stayed 88 GB. No driver, BIOS,
service, SSD or WSL configuration was changed.

An exact-container, host-attached observer prevented the prior WSL idle
lifetime failure. The startup deadline was 360 seconds. Startup pressure stop
remained 20 GiB; 24 GiB was still required for stable readiness. No second
model or GPU probe was started alongside this attempt.

## What happened

| Event | UTC / measurement |
|---|---|
| Container started | 20:10:21.420 |
| Engine began reserving 262,144 KV positions (about 7.2 GiB) | 20:12:42.645 |
| Windows guard triggered a pressure stop | 20:12:43.487; elapsed 142.625 s; 19,746,004,992 B available |
| Lowest guard sample while stop was pending | 886,714,368 B available (0.887 GB; 0.826 GiB) |
| Engine reported allocation failure | 20:13:07.340; request 0.250 GiB after 5.079 GiB in 413 tracked allocations |
| Container finished | 20:13:11.318; PID 0, exit 137, OOMKilled=false |
| Guard confirmed stopped | 20:13:11.377; elapsed 170.516 s |
| Final Windows sample | 89,936,736,256 B available; model no longer running |

Exact engine error:

```text
dmalloc: FAILED requesting 0.250 GiB after 5.079 GiB in 413 allocations (out of memory)
HIP /src/halogen/src/flash_ops.h:157: out of memory
```

The GiB allocation figures are the engine's rounded report, not independently
measured exact byte totals. `OOMKilled=false` does **not** mean no memory
failure: it only describes the container's OOM-killer flag. Both the HIP
allocation error and severe Windows memory pressure were observed.

The guard requested a stop promptly, but driver/process cleanup continued for
about 28 seconds. The observed reserve fell far below the trigger. A stop
threshold is not a reservation or a guarantee of responsive cleanup. Do not
increase limits or weaken the guard to make this configuration appear to pass.

This is a failed capacity qualification, **not** an occupied-256k benchmark
and not proof that every alternative Windows/WSL configuration is impossible.
Earlier experiments with other copy caps are separate failed/limited evidence;
they are not a working fallback certified by this result.

The slower device-counter sampler did not capture the critical sub-1-GB
nadir; the faster guard samples did. Do not substitute the coarse CSV minimum
for the actual observed guard minimum. Neither sample stream establishes an
exact instantaneous per-model physical GPU allocation.

Windows recovered after the container ended. No Windows Display/4101 event
was found in the checked 20:10–20:15 UTC window; this narrow check is not proof
that no GPU/driver warning of any kind occurred. All test processes were
stopped after recovery. The original completed 32k benchmark remains separate.

Further capacity work needs a different, pre-budgeted memory configuration
and safer allocation/cleanup qualification before another large model load.
The publication must label 256k unsupported by the current tested profile.
