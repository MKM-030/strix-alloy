**Serving suite: passed in full. Size sweep: completed in full.**
This is a measured experimental Windows/WSL2 profile, not yet a clean-install
release or a256k/concurrent-session qualification.

## What was run

Unmodified `bench-serving.py` from the official pinned Halogen0.13.8 image,
with its original ten prompts, `serial,mtp 256 low 3`. All60 requests completed
between19:01:14 and19:10:15UTC. The tool passed its greedy-output identity
check across drafters, reported no unstable repetitions or ledger warnings,
and all30 MTP ledger records matched. A supplemental audit also paired all
30 serial engine records, checked mode/output-token identity and recalculated
every rate within the precision of the rounded log fields. No prefix-cache hit.

Prompt lengths were50–69 tokens; outputs were256 tokens except `chat_a`,226.
Thinking was enabled, but the256-token answer budget closed it at token1.
This is not a long-reasoning benchmark. Run order is the upstream order:
serial then MTP for each prompt, repeated three times, without an extra warmup.

## Decode results

The original tool reports **41.20 tokens/s MTP mean** across all ten cases and
three repetitions, with mean commit1.68 per speculative round. Means per case
range32.85–49.48; individual requests range23.32–50.68. Neither range is a
confidence interval or a guarantee for arbitrary prompts.

Supplemental comparison using the SAME engine decode-time boundary for both
modes (rounded to0.1 tokens/s here):

| Included requests | Serial engine tokens/s | MTP engine tokens/s |
|---|---:|---:|
| All three repetitions,30 per mode |30.9 |41.2 |
| First repetition,10 per mode |19.4 |35.9 |
| Second repetition,10 per mode |36.9 |44.0 |
| Third repetition,10 per mode |36.5 |43.7 |

The first repetition is visibly slower. Do not discard it silently or call
later requests independently cold. Serial always precedes MTP, so the overall
difference includes order/cache effects and is not an isolated causal MTP
speedup. The original tool's serial `*` values use HTTP wall time; comparing
those to MTP engine rates would mix timing boundaries.

## Startup and Windows memory

The changed startup guard completed after136.875seconds, with minimum
23,032,864,768B (23.03GB;21.45GiB) available Windows RAM and
30,462,496,768B (30.46GB;28.37GiB) at guarded readiness.

Only the existing startup file-cache advice threshold/cadence changed:
below64GiB, at least1second between operations, at most one in flight.
The guard never issued file-cache advice during timed inference. Its abort
thresholds were NOT lowered. One successful load does not establish a
repeatable installation or guarantee a minimum reserve during driver cleanup.

Engine accounting is72.5GiB in total (~77.85GB), including exact weight
payload73,007,346,240B split into29,002,991,808B copied and44,004,354,432B
registered. Its47.7GiB lookup table remains disk-backed. These figures overlap
with Windows/GPU counters and cannot be added to them. No120GB allocation or
128GiB VRAM unlock is claimed.

During guarded runtime the minimum available Windows RAM was28,441,710,592B
(28.44GB;26.49GiB). Before the deliberate stop it was28,697,194,496B
(28.70GB;26.73GiB). Maximum observed device-wide GPU-adapter usage was
85,356,490,752B (85.36GB;79.49GiB), INCLUDING other adapter clients and driver
accounting. That counter is not an exact per-model physical allocation proof.
Maximum sampled Windows commit was115,084,926,976B, not resident physical RAM.

[193 adapter/Windows samples](upstream-memory-20260924.csv) and
[the memory summary](upstream-memory-20260924-summary.json) are included.
Two overlapping runtime guards supplied1449 samples; no pressure stop or cache
advice occurred during inference. One guard naturally completed its20-minute
interval. The other observed the deliberate post-benchmark container stop;
its later `Container exited during monitoring` event is teardown, not a

a2GiB-limited no-GPU container, outside all timed measurements.

The earlier failed starts and aborted original-suite attempt remain documented
