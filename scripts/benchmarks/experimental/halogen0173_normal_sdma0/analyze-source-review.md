# Bounded source review: normal SDMA analysis

Reviewed 2026-10-09 at root's request, by reading source only. No analyzer, client, test, build, hardware, request, or lifecycle action was executed. The collection/comparison logic has no source blocker for the planned bounded cohort. Two reporting interpretation cautions below should be addressed before calling a positive result a demonstrated engine gain.

Reviewed `analyze.py`, 3,918 bytes, SHA256 `2946de1b935f45d29fa40b8563afd9525c1ff949c97fb2efcfc516d152a24cc8`; `window.py`, 12,061 bytes, SHA256 `f7142d05e8c490d032a1ef485e1b7e535b82641ac726ffdf32506e6a474ca3b0`; `scripts/benchmarks/article_metrics.py`, 8,932 bytes, SHA256 `8d3ceb75adc371b1c79caef2de775c9daf92c97d319fc159e564bea1410d7cb5`; and `scripts/benchmarks/clock_probe.py`, 1,709 bytes, SHA256 `a3f32a4c5c7e423c47ceebdd2f0fe0cd1860d7840c9fd0de10756e887c70a05e`. Findings apply to these exact source versions, not a subsequent edit.

`analyze.py:10–20` excludes each arm's first row, then computes the relative MONOTONIC/RAW spread as `max(ratios)/min(ratios)-1`. It permits at most 0.001 (0.1%) and requires **every** measured RAW/QPC ratio to differ from 1 by at most 0.001. Lines 33–34 apply this both to all three arms pooled and candidate versus each stock arm; line 48 requires pooled qualification for the positive-rate flag. This matches the plan's cross-arm 0.1% gate, preserves raw native rates, and explicitly records that native rates were not normalized. The clock probes are whole-request comparisons and do not independently measure the clock ratio inside each prefill/decode phase; keep that scope when interpreting phase rates.

`analyze.py:27–30` requires four successful rows and identical profile, prompt, request, client and greedy-output/counter baseline across all three arms. It compares output SHA256, accepted, drafted, and finish reason for every row including warmup. The summary means, standard deviations, walls and count sums use only rows 1 onward. The clock gate excludes warmup; minimum memory deliberately includes it.

The acceptance denominator is correct: `window.py:165–172` calls `article_metrics.acceptance` on the measured cohort; `article_metrics.py:28–33` computes `sum(accepted)/sum(drafted)`, rejects invalid accounting, and does not divide by output tokens or count candidate-accepted tokens as native MTP trials. `analyze.py:40–41` retains both measured aggregate numerator and denominator. Line 51 currently says `combined native API MTP+PLD`; use **combined API MTP/PLD draft-token counters** to avoid implying separately measured native MTP acceptance. Native MTP acceptance, if reported separately, needs its own retained numerator and denominator.

`analyze.py:49–50` correctly labels the input as synthetic pseudoprose with 116 repeated calibration units, 8,192 actual input tokens and 128 generated output tokens. It does not describe the benchmark as natural prose. The word spacing in the saved scope string can be tidied for readability without changing the experiment.

`analyze.py:48` treats any positive candidate mean in both prefill and decode against both stock arms, plus clock qualification, as `net_prefill_and_decode_gain_qualified`. The source does retain sample standard deviations and keeps production adoption a separate decision, but this predicate does **not** itself establish improvement beyond sample spread or a repeatable causal gain. Prefer a name such as `positive_means_with_clock_qualification`, or interpret that existing field explicitly as a screening result in the report. Assess stock drift, per-sample spread, phase_ms and wall evidence before adopting; do not convert host copy waits into a token-rate forecast. A failed pooled clock gate leaves raw deltas available with their qualification flags and does not retry a completed cohort for favorable clocks.
